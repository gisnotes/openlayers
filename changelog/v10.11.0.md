# 10.11.0

The 10.11 release improves styling, raster data and OGC service support, and makes the library leaner to load. The highlights are

10.11 版本改进了样式设置、栅格数据与 OGC 服务支持，并使库的加载更加精简。主要亮点包括：

* Canvas styles now evaluate the `color` and `array` operators, and `interpolate` mixes colors in sRGB on both the Canvas and WebGL renderers; a new `interpolate-hcl` operator keeps the perceptual gradient

  Canvas 样式现支持求值 `color` 和 `array` 操作符，且 `interpolate` 在 Canvas 和 WebGL 渲染器上均采用 sRGB 进行颜色混合；新增的 `interpolate-hcl` 操作符可保持感知均匀的渐变

* `ol/source/Raster` gains basic data tile support, and the GeoZarr source can visualize generic n-D datacubes and accepts `storeOptions` for headers and credentials

  `ol/source/Raster` 获得了基础数据瓦片支持，GeoZarr 数据源现可可视化通用多维（n-D）数据立方体，并支持用于请求头和凭据的 `storeOptions`

* WMTS sources no longer derive their extent from the tile matrices, so layers that cover a wider area at low zoom levels are no longer cut off

  WMTS 数据源不再从瓦片矩阵中推导其范围，因此在低缩放级别下覆盖更广泛区域的图层不再被截断

* Tiles that the current view no longer needs are dropped from the queue, and the WebGL text overlay worker is loaded on demand

  当前视图不再需要的瓦片将从队列中丢弃，WebGL 文本覆盖层 worker 改为按需加载

* The `VectorImageLayer` gets crisp rendering on rotated views, with rotated text and point symbols

  `VectorImageLayer` 在旋转视图下可实现清晰渲染，并支持旋转文本和点符号

* New `wrapX` option for `getPixelFromCoordinate` and `getCoordinateFromPixel`, and `projection` options for the WKT format

  为 `getPixelFromCoordinate` 和 `getCoordinateFromPixel` 新增 `wrapX` 选项，为 WKT 格式新增 `projection` 选项

* Fixes for RTL text along lines, nested WFS 2.0 feature collections, empty GeoJSON coordinate arrays, and MouseWheelZoom target cleanup

  修复了沿线 RTL 文本（从右到左）、嵌套 WFS 2.0 要素集合、空 GeoJSON 坐标数组以及 MouseWheelZoom 目标清理等问题


### Upgrade notes

### 升级说明

#### Fixed GeoJSON parsing of geometries with empty coordinate arrays

#### 修复空坐标数组几何图形的 GeoJSON 解析

Previously, a GeoJSON geometry with an empty coordinates array (e.g. `{"type": "Point", "coordinates": []}`) produced a geometry with an empty coordinates array. We have now changed this to match the GeoJSON spec's recommendation to treat such geometries (except `GeometryCollection`) as `null` geometries. This change should not affect application code, unless it had special handling for geometries with empty coordinates arrays.

此前，具有空坐标数组的 GeoJSON 几何图形（例如 `{"type": "Point", "coordinates": []}`）会生成一个带有空坐标数组的几何对象。我们现已将其修改为符合 GeoJSON 规范的建议，将此类几何图形（`GeometryCollection` 除外）视为 `null` 几何图形。除非应用代码对此类具有空坐标数组的几何图形有特殊处理逻辑，否则该变更不会对应用代码产生影响。

#### Fixed: `interpolate` mixed colors differently on the Canvas and WebGL renderers

#### 修复：`interpolate` 在 Canvas 和 WebGL 渲染器上的颜色混合方式不一致问题

The `['interpolate', ...]` operator interpolated colors in the Hue-Chroma-Luminance space on
the Canvas renderer, but component-wise in sRGB on the WebGL renderer. The same style
produced different gradients depending on which renderer drew it, and neither behaviour was
documented. Both now interpolate in sRGB.

`['interpolate', ...]` 操作符此前在 Canvas 渲染器上是在 HCL（色相-色度-亮度）色彩空间中进行颜色插值，
但在 WebGL 渲染器上是按分量在 sRGB 中插值。相同的样式会因渲染器的不同而产生不同的渐变效果，
且这两种行为此前均未在文档中明确说明。现在两者均统一在 sRGB 中进行插值。

Gradients built with `interpolate` over colors will look slightly different on the Canvas
renderer. To keep the previous appearance, use the new `interpolate-hcl` operator:

在 Canvas 渲染器上，使用 `interpolate` 生成的颜色渐变视觉效果会略有变化。
若要保留先前的显示效果，请使用新增的 `interpolate-hcl` 操作符：

```js
// Before
// 变更前
const style = {
  'fill-color': ['interpolate', ['linear'], ['get', 'value'], 0, 'red', 1, 'green'],
};
```

```js
// After - to keep the perceptual gradient
// 变更后 - 保持感知均匀的渐变
const style = {
  'fill-color': ['interpolate-hcl', ['linear'], ['get', 'value'], 0, 'red', 1, 'green'],
};
```

`interpolate-hcl` is only supported by the Canvas renderer for now.

`interpolate-hcl` 目前仅在 Canvas 渲染器中支持。

With the `['interpolate', ...]` operator, channels now keep their fractional part, so operations
applied on top of an interpolated color are more accurate. Code reading back a color from an
evaluated style may now see a fractional channel.

使用 `['interpolate', ...]` 操作符时，颜色通道现在会保留小数部分，从而使基于插值颜色执行的后续操作更加精确。
从已求值样式中读取颜色值的代码，现在可能会获取到包含小数的通道值。

#### The WMTS tile grid extent is no longer calculated from the tile matrices

#### WMTS 瓦片格网范围不再根据瓦片矩阵计算

`optionsFromCapabilities` now only uses an advertised `BoundingBox` as the tile grid's
extent, and `tileGrid.getExtent()` returns `null` when none is advertised. Tile requests
are limited by the advertised tile matrix sizes and `TileMatrixSetLimits` instead, so
layers that cover a wider area at low zoom levels than at high ones are no longer cut off.

`optionsFromCapabilities` 现在仅使用声明的 `BoundingBox` 作为瓦片格网的范围；
若未声明，则 `tileGrid.getExtent()` 返回 `null`。瓦片请求改为由声明的瓦片矩阵尺寸以及
`TileMatrixSetLimits` 进行限制，因此在低缩放级别下覆盖范围比高缩放级别更广的图层将不再被截断。

#### `wrapX` from `optionsFromCapabilities` is based on the tile matrix

#### `optionsFromCapabilities` 中的 `wrapX` 改为基于瓦片矩阵判定

The world is now wrapped when the first tile matrix spans exactly the width of the
projection's extent, instead of when the layer's `WGS84BoundingBox` covers the whole world.
Sources that cover only part of the world on a world spanning tile matrix set - e.g. a
national basemap on `GoogleMapsCompatible` - are now configured with the `wrapX` option set
to `true`. If that's undesired, `wrapX` needs to be overridden to `false`.

现在，当首个瓦片矩阵的跨度恰好等于投影范围的宽度时，将开启世界横向循环（wrap），而不是此前仅在图层的 `WGS84BoundingBox` 覆盖全世界时才开启。
对于在跨全球瓦片矩阵集上仅覆盖世界部分区域的数据源（例如基于 `GoogleMapsCompatible` 的国家级底图），
其 `wrapX` 选项现在会被配置为 `true`。如果不需要此行为，需要手动将 `wrapX` 覆盖设置为 `false`。

```js
// Before
// 变更前
new WMTS(optionsFromCapabilities(capabilities, {layer: 'my-layer'}));
```
```js
// After - to keep the layer in a single world copy
// 变更后 - 保持图层仅在单份世界地图中显示
new WMTS({
  ...optionsFromCapabilities(capabilities, {layer: 'my-layer'}),
  wrapX: false,
});
```

The `Layer`'s `WGS84BoundingBox` is no longer used, because the WMTS specification allows
it to be approximate.

不再使用图层的 `WGS84BoundingBox`，因为 WMTS 规范允许该值是近似值。
